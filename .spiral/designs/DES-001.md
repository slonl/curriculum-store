# Design: NiveauIndex Recalculation Boundary

## Role

Define how `src/index.niveau.mjs` derives `NiveauIndex` during create and
update.

## Why This Exists

`REQ-001` requires create and update to satisfy the same `NiveauIndex`
invariant while preserving update performance. The current implementation has
separate behaviors that can drift: create can short-circuit on own `Niveau` or
existing `NiveauIndex`, while update derives from child indexes only.

## Cultural Influence / Constraints

No explicit culture profile is adopted for this project. The design is shaped by
the project constraint that data-format behavior should remain stable and by the
request constraint that update should avoid broad full-graph recalculation.

## Behavior / Responsibilities

- Use one local recalculation function for an entity's effective
  `NiveauIndex`.
- Recalculation treats own `Niveau` as authoritative.
- If own `Niveau` is absent, recalculation uses the de-duplicated effective
  niveau values of relevant children.
- `Vakleergebied` children are excluded from niveau propagation.
- Create walks the graph from root entities and recalculates descendants before
  parents, ignoring any existing derived `NiveauIndex` as source state.
- Update recalculates changed entities when their own `Niveau` or relevant
  children changed, then propagates recalculation to parents when the value
  changed.
- When update needs a child contribution and the child already has
  `NiveauIndex`, use it. If the child has own `Niveau` but no populated
  `NiveauIndex`, derive from the child's own `Niveau` rather than missing it.

## Boundaries

What belongs here:

- `src/index.niveau.mjs` create/update derivation.
- Focused tests for the invariant.

What must remain outside:

- Data-format changes.
- REST API behavior changes.
- Excel import/export.
- Search, registration, frontend, or unrelated index refactors.

What change should this boundary protect us from:

Create and update should not silently encode different meanings for
`NiveauIndex`.

## Supporting / Intrinsic Work

| Support | Why necessary |
|---|---|
| Rewrite stale regression tests | Current file encodes rejected assumptions |
| Preserve `Vakleergebied` exclusion tests | Related links must not become child propagation paths |

## Alternatives Considered

| Alternative | Why not now | Evidence / trade-off |
|---|---|---|
| Full graph recalculation on every update | Too likely to be slow for editing workflows | Maintainer explicitly allowed update shortcuts for performance |
| Keep create short-circuiting on existing `NiveauIndex` | Violates derived-data source boundary | `SRC-001` says create must not use `NiveauIndex` as source state |
| Treat stale regression tests as authoritative | They encode a rejected old assumption | Maintainer correction in `SRC-001` |

## Complexity / Maintainability Check

- Concepts introduced: one effective niveau helper shared by create/update.
- Dependencies introduced: none.
- Expected change radius: `src/index.niveau.mjs` and focused tests.
- Replaceability considerations: helper stays local to the module.
- What would make this harder for a future agent/human to change: mixing
  persisted derived state with source fields during create, or letting create and
  update maintain separate derivation logic.

## Verification Plan

- Focused tests cover:
  - own `Niveau` is authoritative;
  - child propagation is de-duplicated;
  - create ignores stale existing `NiveauIndex`;
  - descendants are indexed even when ancestors have own `Niveau`;
  - update handles newly linked children with own `Niveau` but no
    `NiveauIndex`;
  - `Vakleergebied` remains excluded.
- Existing index update tests continue to pass.
- Full `npm test` passes or unrelated failures are identified.

## Deferred Decisions

- Performance characterization on full production-like datasets.
- Broader index invalidation strategy if future evidence shows parent
  propagation is insufficient.
