# Request: NiveauIndex Create/Update Invariant

## Operationalized Intent

The maintainer and customer need `curriculum-store` to maintain `NiveauIndex` as
correct derived data during create and update, so graph entities can be filtered
efficiently by their materialized `Niveau`.

## Upstream Understanding

`UND-001` records the accepted interpretation: own `Niveau` is authoritative;
entities without own `Niveau` derive de-duplicated values from relevant
children; `Vakleergebied` is not a child propagation path; create rebuilds from
source fields; update may use existing `NiveauIndex` as a performance shortcut.

## Intended Audience

- Maintainer and colleagues developing `curriculum-store`.
- SLO technical contact validating dataset behavior.
- Downstream opendata.slo.nl workflows that rely on correct materialized
  `Niveau` filtering.

## Observable Desired Outcomes

### invariant-create

A fresh index create pass rebuilds each entity's `NiveauIndex` from source
`Niveau` fields and graph relations, ignoring existing derived `NiveauIndex`
state.

### invariant-update

An update pass keeps changed entities and affected ancestors consistent with the
same invariant without requiring broad full-graph recalculation.

### invariant-related-links

`Vakleergebied` remains excluded from parent/child `NiveauIndex` propagation.

## Assumptions / Ambiguity

| Claim | Provenance | Evidence / Question |
|---|---|---|
| Own `Niveau` is authoritative and exactly determines that entity's `NiveauIndex` | explicit | `SRC-001` |
| Existing `NiveauIndex` is derived and not source state during create | explicit | `SRC-001` |
| Update may use existing `NiveauIndex` for performance | explicit | `SRC-001` |
| The exact update performance envelope is acceptable if changes remain local to affected entities/ancestors | inferred | Verify by avoiding broad traversal; characterize if this becomes uncertain |

## Non-Goals

- Changing `jsontag` or `od-jsontag` formats.
- Changing REST API behavior.
- Changing API authorization-header behavior.
- Changing Excel import/export behavior.
- Refactoring unrelated index, store, search, registration, or frontend code.
- Solving dependency audit findings or package-lock drift unless it blocks this
  cycle.

## Constraints Already Known

| Constraint | Source | Effect |
|---|---|---|
| Data-format compatibility is high priority | Project context | Keep changes inside derived index behavior |
| `Vakleergebied` is related, not child propagation | `SRC-001` | Exclude it from propagation and parent-link assumptions |
| Update cannot casually become full graph recalculation | `SRC-001` | Preserve performance-conscious update behavior |

## Nearest Important Uncertainty

Whether the existing create/update implementation can satisfy the invariant with
a small local correction, or whether update needs a broader invalidation strategy
for child changes.

## Risks

| Risk | Horizon | Why It Matters | Evidence / Action |
|---|---|---|---|
| Tests preserve rejected old assumptions | near-term | Would encode the wrong behavior and make the fix misleading | Rewrite tests around `UND-001` |
| Update fix recalculates too broadly | near-term | Could make editing slow on real data | Keep update bounded and use existing `NiveauIndex` where valid |
| Real dataset exposes a different propagation edge | deferred | Synthetic tests may miss schema-specific relations | Retain for follow-up if focused tests pass but manual/system checks fail |

## Acceptance Shape

The cycle is accepted when focused tests demonstrate the three invariant
outcomes, existing relevant index tests still pass, and the full
`curriculum-store` test suite passes or any unrelated failure is explicitly
identified.
