# Orphan-only deletion guard verification

Observed on 2026-10-14 for implementation commit `e80abbb` on
`spiral/CYC-20261014-7EGHR-2-orphan-only-guard`.

## Focused command behavior

`node --no-node-snapshot test/orphans.mjs` completed with 21 passing
assertions. The checks demonstrate that:

- entities with no `root` property and with an empty `root` array are accepted;
- soft deletion retains entity content and its JSONTag class;
- linked entities, schema root types, `KerndoelUitstroomprofiel`, `Deprecated`,
  entities with an unknown schema type, and missing entities are rejected;
- a mixed selection is rejected before the earlier valid orphan is changed;
- an entity linked after listing is rejected using current state; and
- `deleteEntity` without `orphanOnly` preserves its previous behavior.

## Published runtime and restart

`node --no-node-snapshot test/simplystore-runtime.mjs` completed with 17
passing assertions. Through the running SimplyStore HTTP interface, an
`orphanOnly` deletion command reached `done`; querying the entity returned
`[true, "ChildType"]`, showing the object remained present, typed, and marked
deleted. After stopping and restarting the store against the same disposable
data, the same result was returned.

The first attempt inside the restricted filesystem sandbox could not bind the
test's temporary port (`EPERM`). The recorded passing run was repeated with
localhost binding enabled; this was an environment restriction rather than a
product failure.

pre-existing Tap coverage threshold makes the default command exit nonzero even
when all assertions pass. The pre-existing ESLint 9 configuration gap was not
