# Guard orphan-only deletion at the store boundary

Branch: `spiral/CYC-20261014-7EGHR-2-orphan-only-guard`, created from `main`
at `05ad3e7`. Branch identity was checked when opening the cycle.
Status: Ready for maintainer evaluation.

Goal: satisfy `REQ-20261014-7EGHR-1` by making `curriculum-store` revalidate
orphan-only deletion commands atomically against current state, while preserving
ordinary deletion behavior and the existing soft-deletion format.

## Analyze

The current REST API sends `orphanOnly: true`, but the current store command
path ignores it. The missing store-side check is the safety boundary: listing
orphans in the API is not sufficient because graph relationships can change
before the command executes.

An old standalone `curriculum-store` working tree contains an uncommitted
prototype and focused tests. Git history, reflogs, stashes, and reachable refs
showed no commit containing `orphanOnly`; the prototype was never merged or
released. It is evidence for a narrow port, not a branch to merge wholesale,
because that tree also contains unrelated generated data and schema changes.

## Plan

- Add a preflight pass in `src/commands.mjs` before any command mutation.
- Reuse the orphan definition already implemented by the REST API: entity and
  schema type exist, type is not a root type, type is not
  `KerndoelUitstroomprofiel` or `Deprecated`, and `root` is absent or empty.
- Add focused command-level tests for valid, invalid, mixed, stale, and ordinary
  deletion cases.
- Add a runtime restart test proving guarded soft deletion persists.
- Expose `QUERY_MEMORY_LIMIT`, defaulting to 64, and document its relevance to
  large orphan scans.
- Run focused tests, the store suite without coverage collection, and syntax or
  configuration checks proportional to the change.

Generated data/schema changes, UI behavior, hard deletion, changing the orphan
definition, repairing repository-wide coverage thresholds, and adding a new
ESLint configuration are explicitly outside this cycle.

Pause and re-plan if the current schema contradicts the REST API orphan
definition, if atomic validation requires a data-format change, or if the
runtime test exposes a persistence behavior different from the existing soft
deletion contract.

## Act

Implementation commit `e80abbb` adds the atomic command preflight, focused
command tests, a published-runtime restart assertion, and the configurable
query-memory option with documentation. It does not include the unrelated
generated data/schema changes found in the old standalone working tree.

`EVD-20261014-7EGHR-3` records the verification results. The implementation
followed the planned boundary without a data-format change: guarded deletions
still use the existing `deleted = true` representation, while an invalid
selection now fails before the mutation loop begins.

## Evaluate

The requested behavior is implemented and automated checks are green:

- focused guard tests: 21 assertions passed;
- published runtime/restart test: 17 assertions passed;
- full suite with coverage collection disabled: 69 assertions passed; and
- query-memory default/override checks produced 64 and 96 as expected.

The normal Tap coverage threshold and missing ESLint 9 configuration remain
known repository-tooling issues outside this cycle. No production-like manual
browser session was performed; the current evidence covers the store boundary
and its published HTTP runtime.

The cycle is ready for maintainer evaluation. Readiness does not imply
